## Decisions

| Decision | Choice | Decided |
|---|---|---|
| Extension language | Lean 4 | Prototype |
| Who owns the process | Lean. The editor is a Lean program; Rust is a library it calls and pulls events from. Rust never calls Lean | 2026-11-10 |
| The split | Rust: text storage, layout, rendering, the window, processes and terminals, parsing. Lean: editor state, the command loop, every feature | 2026-11-10 |
| Editing style | evil (Vim-style modal), written in Lean, from the first milestone | 2026-11-09 |
| First front end | GUI (winit, wgpu). The frame is device-independent, and a cell grid shaper and renderer are built early as test adapters, so a terminal front end stays possible | 2026-11-09, revised 2026-11-11 |
| Lean editor API | Interfaces with a real binding and a pure model, not direct library calls. An interface is a port (requests, and a reply type for each), and a command or a job is a program over it, run against either handler; not type classes | 2026-11-09, representation 2026-11-11 |
| Config session | A pure core over an elaborator port and a source port, with Lean's elaborator behind one adapter. `setup` is a program over a setup port of its own, and a command is the value it registered. A store is a whole-value cell in the editor's state, not a request of the editor's port. Every thread Lean creates has a 64 MiB stack, so runaway recursion in config ends the process quickly | 2026-11-11 |
| Job system | Built on plain tasks and promises, not on Lean's async library: a wait is a promise completed by a completion pump, so a job in a wait holds no thread. Cancellation is not a reply, so a `try`/`catch` cannot resume a cancelled job. A job finishes with a command, which the editor thread runs through the command loop, like any command. A command starts a job by the name it is registered under, with plain arguments: the request cannot carry the job, so the loop hands the starts of a command that ran to its end back to its host, which starts each for whoever registered it. Jobs share their owners with the registry, and a reload that installs cancels the old config's jobs. Timers are a Rust service behind the completion queue. The pool keeps Lean's size, one thread a core, and is warmed at start-up | 2026-11-11, started from commands 2026-11-14 |
| Platforms | macOS and Linux build and pass the gate; Linux was run on aarch64 in a container. The system compiler compiles the glue and links on both, and the C entry point takes `main`'s place by a linker entry symbol on macOS and by `--wrap=main` on Linux. Windows has not been attempted. No dynamically linked build: it saves disk and nothing else | 2026-11-12 |
| Window port | A crate of its own, `editor-platform`, with no dependencies: what a window reports as plain data, a scripted fake and a contract. `editor-platform-winit` is the adapter, and only it may name winit. The window is run by the main-thread service onto the editor queue, each event stamped when it was reported, and Lean closes it. A key carries its logical and physical identity and the modifiers, as W3C UI Events names, with the text it produced beside it; a pointer its action, position, button and modifiers; a resize the size and scale. The winit adapter produces all of it: the modifiers as winit last reported them, a key's text none for a release, for a control character and for a key pressed with Control or the system key held (that last awaits the owner), and the window's size reported as it opens. A window has a second listener, the drawer, for whatever draws in it: it is told that the window opened, with its native window as the port's own data, its size and its display's refresh rate, before anyone hears of the window; a new size, a new refresh rate, damage, hidden or shown; and that it is closing, last. Redraw is on demand: winit's loop waits, and the adapter never asks it for a redraw. The contract holds what is reported and what is told, and the real window is held to it under Xvfb; the drawer's shape awaits the owner | 2026-11-12, identity 2026-11-13, mapping and drawer 2026-11-14 |
| Clipboard port | `editor_platform::clipboard`: text read from the system clipboard and text written to it, with a fake that keeps text in memory and a contract of four properties. It is the Rust library's seam below the clipboard interface in Lean, which is the command loop's, and decides nothing of what the editor asks of a clipboard. `editor-platform-arboard` is the adapter, over arboard pinned exactly with its default features off; it needs no window, keeps one clipboard for its life, and reads an empty clipboard as no text. The gate touches no clipboard: the adapter is held to the contract under Xvfb, in one process and across two. Nothing binds it to Lean yet; a Wayland session is reached through XWayland or not at all. Where the port lives awaits the owner | 2026-11-14 |
| The editor's port | A composite: its requests are a sum of sub-ports (text, display, watch, and the requests about the editor state), each reply its sub-port's. The watch port is the interrupt flag and the job clock, so the loop that asks them stays one pure program. A command is `EditorM`, a program over it; a sub-port's programs (`TextM`, `DisplayM`, `WatchM`) are lifted into it automatically, so config written at `EditorM` uses every text operation as it is. A refusal stays a `TextError`, the display's mapped to the text's of the same name; what the editor state refuses is a value in the request's reply. Each runner's state is the product of its sub-ports', but for the editor state: the command loop holds it and answers a command's state requests itself, with one pure handler, before the command's program reaches a runner, so the loop stays the one writer of editor state and rollback stays "keep the state from before". The editor API a command is written with is programs over this port; every operation that reaches the library has a case run on the models and on the real binding | 2026-11-13, state requests 2026-11-14 |
| Display contract | Lean publishes a scene of plain data after each command: views by handles (a snapshot, a scroll anchor and selections as markers), faces by name only. Layout answers two queries in the same call, the rows a view shows from its anchor and the position some visual lines away with the goal x passed back; Lean keeps no layout. A model lays text out in fixed-size cells, and one contract holds it and the real binding (over a fake shaper of that cell size) to the same properties. A key, a pointer and a resize cross the editor queue as words beside the event: the layouts are the table in `editor-ffi`'s `window.rs` | 2026-11-13 |
| Layout | `editor-layout`, ours, over a `Shaper` port whose fake gives fixed-size glyphs and whose real adapter is over Parley. Tabs are expanded before shaping; a row longer than 4096 bytes is laid out in segments. One immutable entry per segment, keyed by row and moved through the edit log's patches, rebuilt from the snapshot when a patch is refused; storage is sparse, with estimates and eviction, and no summarised tree yet. Decorations come from sources, asked for visible rows only; a face that sets no font attribute is paint only, and shapes nothing again. Positions, cursors and selections are found by a line's cells, a character's even share of its cluster's glyphs, so they are right whatever the order of a line's glyphs and however many characters a glyph draws. The frame is an immutable value with a content hash per row, and carries resolved paints, the id of the font each glyph is drawn in, the table of those fonts and the shaper's generation, never a face and never an atlas. A view's status fields are one row at its bottom. A snapshot handle reaches its document's log and markers, so Lean's display binding needs only its table of snapshots. Layout lays out at a scale it is told, 1 until then: it multiplies a face's lengths by it in one place, as it asks the shaper for a font, so the `Shaper` port stays in physical pixels and the scale is in the cache key as the font; a change of scale alone shapes the rows a view shows again; frames and the queries' answers are physical pixels (the owner, 2026-11-14; where inside layout, and that nothing is rounded to whole pixels, await the owner). Who tells it a window's scale is so far one example; how a scene published from Lean is laid out at its window's scale is open. Who writes the cache while a render thread reads it awaits the owner ([concurrency.md](concurrency.md)) | 2026-11-13 |
| Shaping | `editor-shape-parley`, the `Shaper` port's real adapter, over Parley and fontique pinned at exactly 0.13.0; no type of either is public, and `deny.toml` lets no other crate depend on them. One Parley layout for each segment shaped, kept and broken again at another width; never `PlainEditor` or a layout of a document. Fonts come from a font set: given files as bytes with the system's fonts off, which every test uses over fixture fonts checked in under `tests/fonts`, or the system's, checked on demand. A glyph names the resolved font it is drawn in, fallbacks included, in a table that travels with the frame under a generation. Glyphs are in visual order with every line's base direction left to right; breaking is Parley's, at words; a line is as tall as the fonts on it; a carriage return and the Unicode separators break no line. It is built and held to the port's contract, and linked by nothing yet: the display handle stays on the fake until something needs real metrics through it | 2026-11-13 |
| Renderer port | `editor-render`, a crate of its own over `editor-layout` alone, owns the `Renderer` port: one method, a frame and a target in, what drawing it cost out. It publishes the port's fake and its contract, which both real adapters run, and holds what every back end shares: a mailbox where a newer frame replaces one not yet drawn; a scheduler that is a pure function of the demands and the time; the rule for which rows are built again, by their content hashes; the frame journal, with the times of each frame's input, draw and presentation; the counters; and the loop over them, which draws on demand, at most once a refresh, and waits with no deadline when idle. Time is a port with a fake. `editor-ffi` starts the render thread, one for the life of a window: a session makes the renderer when the window opens, on the window's thread, runs the loop on a thread of its own with the clock that stamps input, turns what the window tells into words left with the loop, and at closing joins the thread and drops the renderer on the window's thread. A hidden target is not drawn on, and what was asked meanwhile is served by one draw when it is shown. The render thread owns the renderer alone and never lays out ([concurrency.md](concurrency.md)). Nothing reaches the session from Lean yet. Where the port lives, and that the render thread and not the main thread draws, await the owner | 2026-11-14 |
| Faces | A face is nine optional attributes: family, size, weight, slant, foreground, background, underline, strike-through, line height. Lean defines them, as a theme, an ordered list of definitions that config appends to in `setup`; Rust merges them, in layout, attribute by attribute: the selection over the view's decorations, a later one over an earlier one, over the face `default`, over base values, and a later definition of a name over an earlier one. Family, size, weight, slant and line height are a font, named to the `Shaper` port by a spec; the rest is paint. A length a face states (a size, a line height stated as a length) is in logical points, one physical pixel at scale 1, so `size := 14` is the same apparent size on every display; layout multiplies, and Lean states points and knows no scale for faces (the owner, 2026-11-14). The types keep the names they had when a theme stated physical pixels (`Pixels`, `Length::pixels`); renaming them awaits the owner. The theme crosses in the published scene's words, behind a presence, only when it changed; Lean's scene and the display interface are unchanged. Merging in Rust awaits the owner's confirmation (task `display-pipeline-text-core-pitfalls`) | 2026-11-13 |
| Rope | `ropey`, pinned at exactly 2.0.0-beta.1: indexed by byte, with rows split by line feed alone and UTF-16 counted in the tree, edits that return an error, and clones that share nodes. One private module of `editor-text` names it. `crop` is the fallback; a summarised tree of our own is left to the display layers | 2026-11-12 |
| Text model | UTF-8 only. A byte of a file that is not valid UTF-8 is kept as one reserved character, `U+10DC00` plus the byte, and saved as that byte, so an unedited save is byte-identical. Line endings are kept as they are. Positions are byte offsets on character boundaries; a row ends at a line feed alone; a point's column is in bytes, in UTF-16 code units or in cells, and no conversion clamps. A snapshot is the text at one revision, immutable and shared between threads, and is the only read view | 2026-11-12 |
| Edit model | Change sets on Helix's model: retain, delete and insert in bytes, in one normal form, for a text of one length. They apply, compose and invert, and map a position with a bias. A transaction is a change set plus optional selections, and applying one, all or nothing, is the one way a text changes and one revision. Ours: no published library counts in bytes over our rope or has the log | 2026-11-13 |
| Edit log | One entry for each applied transaction: its revision, an opaque 64-bit origin whose meaning is Lean's, and its changed ranges with four points each, from which the three tree-sitter takes are derived. Consumers pull one coalesced patch since a revision; a subscriber is a revision the consumer keeps. A range is traced to the entries that wrote it by walking the log. The log is dropped only when Lean forgets up to a revision | 2026-11-13 |
| Anchors and selections | An anchor is an offset and a bias, mapped at each transaction as Emacs moves its markers. A text holds markers, each an anchor or a selection under an id, and moves them all with every transaction it accepts. A selection is ranges of two offsets with one shape (exclusive, inclusive, line, block), kept sorted and merged, with a primary; its ends move as anchors, with biases that follow from the shape. What it covers is computed against a snapshot, in cells: a character, or a carriage return and line feed together. Evil's states map onto the shapes; its rules stay in Lean. Ours, with no library | 2026-11-13 |
| Motions | Motion primitives are questions of the text port, answered in Rust by walking the rope from a position, a cell at a time, so a motion moves over exactly what a selection covers: the next and the previous cell; the start and the end of the next and the previous word and WORD; the start of a line, its end and its first non-blank; the ends of the text; and rows up or down at a column counted in cells, which a point's column can be counted in too. A word character is an ASCII letter, digit or underscore or any character from U+0080 up, a rule the pure model can state: Vim's on ASCII, and not beyond it. One row and a range are read without the whole text. Which key runs which motion, counts, the wanted column and keeping a cursor on a line are evil's, in Lean. Ours, with no library | 2026-11-13 |
| Undo | In two halves. Rust keeps the inverse of every applied transaction and applies the inverse of a run of consecutive revisions as one transaction, where the text is in the state the run ended in; it hands back the selection in force before the run, and deleted text never leaves it. The revision only grows: an undo is a new revision that returns the text to an earlier state. The undo tree is Lean, over those two requests of the text port: groups whose boundaries the caller sets, undo, redo and branches, reverting the open group, and the state last saved. Every undo policy is Lean's, so other undo styles are written over the same primitives. Ours, with no library | 2026-11-13 |
| Files | An `Fs` port that `editor-text` defines, with a published fake and a contract; `editor-fs-std` is its adapter over `std::fs`, a crate of its own, held to the contract by its own tests in a temporary directory. A load reads a file once up to the caller's limit, refuses a binary one, counts its line endings and changes none. A save is a temporary file beside the file and a rename, with the file's permissions, and is refused when the file on disk is not the one that was loaded, unless the caller overrides. One service thread in the library works loads and saves in order, behind the completion queue. The logic's tests make no real file, which the linter and `cargo-deny` hold. In Lean, load and save are requests of the job port, which a job awaits, and a refusal is a value. A job reads a snapshot a command took, by its id, from the table of snapshots the editor thread publishes and alone writes; what a job's load makes is the job's, named by a second kind of id, until the job's command takes it into the store, on the editor thread, and the runtime releases what the job held once that command has run. On the buffer's side: a buffer keeps its file's path, the stamp the last load or save answered and a line ending of its own, and its saved state stays in its undo tree. A path is matched to an open buffer by equality of the path string. Open and save are each a command, a job and the job's command: the buffer is made when a load's result is delivered, so the window does not change before the file is known to exist, and a save in flight is recorded in the editor state, so that its result is delivered by one request that cannot be interrupted and a second save is refused when it is asked. The line ending decides only the line break a command inserts; nothing is translated. The load limit is 1 GiB. Ours, over `std`, with `tempfile` for tests | 2026-11-13, buffers and commands 2026-11-14 |
| Vim scheme | Vim's grammar is one input scheme, pure Lean over a registry of Vim states: a key is bound to a part of speech named by its vocabulary name, a key sequence parses to an edit (a move, an operator over a target, a command), and the edit compiles to an invocation. Counts in any position multiply, and no count is not a count of 1. A register is named after a prefix bound in a keymap. The visual selection is not in the scheme's state: an operator in a visual state is an edit over the selection. Which Vim state a view is in is in the scheme's state, by view, so the next key is looked up in the new state's keymaps with no editor API. A key is walked through the active keymaps and then the state's, as one walk. The last edit that changed text is kept as a value, with the text typed in the insert session it began, and the repeat key is a part of speech that yields it to replay. The default states and bindings are data in a module of their own. A scheme is told when the minibuffer's view opens, and the scheme contract holds every scheme to taking typed text there; the Vim scheme then puts the view in the state its registry names for it, by default a fifth state, `minibuffer`, where typing is text, `RET` accepts and `<Escape>` cancels. A state's record says the shape of its selection, and the scheme reports each view's state to the core: its cursor, its name as a status field, the shape, and whether a motion extends the selection, the view is in an insert session and it takes text. What its invocations run is evil ("Evil's states and motions", "Evil's operators, registers, undo and repeat") | 2026-11-13, the minibuffer's state and the report 2026-11-14 |
| Evil's states and motions | Built: Vim's states and motions on the editor API, compiled into the executable, so the editor moves and inserts with no config. A view's wanted column is kept on its window, in the editor state, with the offset the cursor was left at: a vertical motion uses it only while the cursor is still there, so nothing has to clear it. It counts cells, where Vim's counts display columns. A Vim state's record says the shape of its selection, and entering a state reshapes the selection by one rule: the record's shape, both ends kept where operators act on the selection and collapsed onto the head otherwise, one cell back when an insert ends. A scheme reports what it knows of a view (its cursor, its status fields, the selection's shape, whether a motion extends, whether it is in an insert session, whether it takes text), and the loop hands the report to the command it runs and to the scene; the scheme contract holds a key that yields nothing to leaving it as it was. A motion is a vocabulary entry, a name and a function from a position and a count to a raw target, over the text port alone; fifteen are compiled (`h j k l w b e W B E 0 ^ $ gg G`), composed from the motion primitives, and one command runs them. Where a head may rest is a rule of the state applied after the motion, so a motion answers a raw target an operator can use: off the line break in normal state, on any cell in a visual state, anywhere in insert. The empty last row of a text that ends in a line feed is no line for a cursor outside insert state. One insert session is one step of the history: the loop leaves a buffer's undo group open while a view of it is in a session, and a committed text is inserted only where the view takes text. The oracle is Vim's documented behaviour written out case by case, checked against Vim 9.1 by hand; no test runs Vim | 2026-11-14 |
| Evil's operators, registers, undo and repeat | Built: `d c y` over a motion, over lines and over a visual selection, `x p P o O`, `u`, `C-r` and `.`, compiled into the executable. An operator is a vocabulary entry, and one command composes it with what it acts on; a motion says how an operator takes it (exclusive, inclusive, whole lines) and when it fails. What an operator takes is seven rules from Vim's documentation, applied in order, and what each operator does with cells, with no cell and with lines is a table; both are checked against a table of every operator over every motion in five situations, written by hand from Vim 9.1's results, which a check holds complete against the default key tables, and by a sweep. A command can give up with a reason: it is rolled back, the reason is in the echo area, and the scheme goes back to its state at rest, which is how an operator whose motion fails is cancelled as Vim cancels it. A command can also break off with a reason, which keeps what it did and puts the scheme back at rest the same way: an operator whose motion moved before it failed leaves the cursor where the motion got to, as Vim does. Registers are a text and whether it is line-wise, by name, in the editor state; evil keeps the unnamed one. The system clipboard is a port with a model and a contract, a sub-port of the editor's, whose refusals are values; a command writes it as its last request, since it is not rolled back; the real adapter is the display pipeline's and a host with no window keeps one of its own. Every edit of evil's carries the selection from before its command, so `u` restores the text and the cursor from before a change (the phase's rule, not Vim's) and `C-r` what the change left. The Vim scheme keeps the text typed in the last change's insert session, a committed text included, and its repeat key, a part of speech, hands the change to a command that replays it as one step, with the command the registry holds for the change's name: a command can have the loop run another inside it, looked up as a key's invocation is, so config's command of a name evil registers is what `.` replays. Proved on the text model: `x` then `u` restores the text. Recorded departure from Vim: a cursor cannot rest in the empty last row | 2026-11-14 |

| Rendering stack | wgpu on every platform, behind the `Renderer` port. Existing libraries are preferred even when immature (Parley), each behind a port; we write our own only where none fits. For drawing none fits: neither Vello nor glyphon draws subpixel text at its current version, so the glyph atlas and the quads are ours, on wgpu, with `swash` rasterising and `etagere` packing ([rendering-prior-art.md](rendering-prior-art.md), "The drawing library, as chosen"); the choice awaits the owner. As built in `editor-render-wgpu` (wgpu 30.0.2, swash 0.2.10, etagere 0.3.0, pollster 1.0.1, each pinned exactly): one painter, with a CPU compositor behind it for a machine with no GPU and wgpu behind it for one that has; subpixel antialiasing below scale 2, blended in linear light by a coverage for each channel; a glyph cache in which what is on screen is never evicted, with a bound; rows drawn again from what was kept. The gate compares the CPU's picture with one reference image and validates the GPU's calls without drawing; a real GPU's picture is compared on demand. A renderer made on a window presents to its surface: in the first sRGB format the surface offers, with `Fifo` at a frame latency of 1, chosen by reading and not measured ("Present mode and pacing"); an outdated surface is configured again and tried once, and an occluded one is not presented to. A window's picture is compared with the CPU's on demand: it has been on llvmpipe under Xvfb, and not on Metal | 2026-11-10, revised 2026-11-13 and 2026-11-14 |

| Runaway code | Not a design driver: an interrupt flag checked at API calls, no watchdog. The flag is the Rust library's, a count raised as the interrupt key arrives, before it is queued; which key, when it is asked and when it is lowered are Lean's. A command a key runs is asked before each request and stops there, and the loop lowers the flag as it takes the key off the queue | 2026-11-10, flag 2026-11-13 |
| Command dispatch | The loop runs one input scheme for the editor and holds its state. A key press is stepped through it, and the invocation it yields is looked up by name (compiled commands, then config's of the same name in their place) and run with the focused window, its arguments, its keys and what the scheme reports of the focused view after the key. A failure goes to the echo area; a refused or interrupted command, and one that gives up with a reason, is rolled back by reverting each undo tree to the state kept before it and putting back each window's markers, and a move in the history is not taken back. Every command goes through the same dispatch, a key's, one run by name and a finished job's: guarded against the interrupt at each request that reaches the library, its requests about the editor state answered from the loop's state, rolled back to the state from before it if it does not run to its end, and followed by a scene. What a command closed or removed is given up only once it has run to its end, and so is the snapshot of a save it ended. Config binds a key sequence to a command name from `setup`, by owner, and a reload replaces config's bindings. A command slower than a threshold is logged. The first compiled commands the executable ships are the file commands, `open-file` and `save-buffer`, with their compiled jobs, which a reload does not cancel, the minibuffer's, `minibuffer-accept` and `minibuffer-cancel`, evil's eighteen, and the ex line's four. The loop closes each buffer's undo group after every event, but for a buffer a view in an insert session shows. An invocation no key yielded is run the same way: a command run by its name, the continuation of a prompt that was accepted, and an invocation a command asked to be run after it, each of which the loop hands back with the step and its host runs before the next event. | Prompts | A command asks for a string without waiting for it: it names the command that receives the answer, as an invocation, and runs to its end. | The ex command line and quit | The ex line is one command, `ex`, that asks for a line with a prompt and has the line's command run after it, as a step of its own. A line is its first word, the ex name, and the rest, one argument kept whole; Vim's `!`, ranges and a leading colon are not read. An ex name is a binding to a command's name, in the registry by owner, with whether it takes an argument, so config's binding of a shipped name runs in its place until a reload drops it, and the command a line runs is an ordinary command whose errors go to the echo area under its own name. A command cannot end the process: it asks, which is a flag of the editor state, and the loop's step says stop once no buffer that holds a file has unsaved changes and no save is in flight. So `q` refuses for a modified buffer of a file, waits for a save in flight, and is withdrawn if that save is refused; a modified buffer with no file never blocks it, which departs from Vim. `wq` starts the save and asks to quit only if it started. A reload a command asks for is a one-shot output of the step, which the host feeds its reload reducer. The headless driver ends its script, with status 0, when the loop has ended by itself. | Completion and fuzzy matching | A prompt may be asked with candidates, from a function the asking command's `prompt` runs once; the open prompt keeps them as plain data, with what it has listed and the choice. | Modes | A mode is a record in the registry, by owner: a name, a parent, the roles it fills and its local commands under suffixes, each naming a command, and an on-enter action given the view. Roles are names the core curates, seven to start (next and previous item, activate, quit, refresh, toggle, mark); a role is added for an action that recurs, with one meaning, in modes with nothing else in common.
