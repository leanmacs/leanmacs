## Decisions

| Decision | Choice | Decided |
|---|---|---|
| Extension language | Lean 4 | Prototype |
| Who owns the process | Lean. The editor is a Lean program; Rust is a library it calls and pulls events from. Rust never calls Lean | 2026-11-10 |
| The split | Rust: text storage, layout, rendering, the window, processes and terminals, parsing. Lean: editor state, the command loop, every feature | 2026-11-10 |
| Editing style | evil (Vim-style modal), written in Lean, from the first milestone | 2026-11-09 |
| First front end | GUI (winit, wgpu). The frame is device-independent, and a cell grid shaper and renderer are built early as test adapters, so a terminal front end stays possible | 2026-11-09, revised 2026-11-11 |
| Lean editor API | Interfaces with a real binding and a pure model, not direct library calls. An interface is a port (requests, and a reply type for each), and a command or a job is a program over it, run against either handler; not type classes | 2026-11-09, representation 2026-11-11 |
| Config session | A pure core over an elaborator port, a source port and two package ports, with Lean's elaborator behind one adapter and Lake's TOML loader behind another. `setup` is a program over a setup port of its own, and a command is the value it registered. A store is a whole-value cell in the editor's state, not a request of the editor's port. Every thread Lean creates has a 64 MiB stack, so runaway recursion in config ends the process quickly | 2026-11-11 |
| Config as modules | A config directory is a Lake package: a root, `init.lean`, whose `setup` alone the editor runs, and config files under `Config/`, each a module that writes its own header. A file may import a config file, a module of the package set, and `Init`, `Std` or `Lean`; anything else is refused. The base grows with what config imports and does not start with everything linked. A reload elaborates a changed file and the files that import it. The editor generates the lakefile and the toolchain file; the old form, headerless files in byte order, is refused and converted by `mise run config-migrate`. The bundle carries `Lean`'s module files | 2026-11-19 |
| Job system | Built on plain tasks and promises, not on Lean's async library: a wait is a promise completed by a completion pump, so a job in a wait holds no thread. Cancellation is not a reply, so a `try`/`catch` cannot resume a cancelled job. A job finishes with a command, which the editor thread runs through the command loop, like any command. A command starts a job by the name it is registered under, with plain arguments: the request cannot carry the job, so the loop hands the starts of a command that ran to its end back to its host, which starts each for whoever registered it. Jobs share their owners with the registry, and a reload that installs cancels the old config's jobs. Timers are a Rust service behind the completion queue. The pool keeps Lean's size, one thread a core, and is warmed at start-up. A job may post a command by name with plain arguments while it runs, answered at once; its host runs each on the editor thread, in order and before the job's own command, and drops a cancelled or removed job's. A job may read a published snapshot's text, answered at once | 2026-11-11, started from commands 2026-11-14, posts 2026-11-16, snapshot reads 2026-11-17 |
| Platforms | macOS and Linux build and pass the gate; Linux was run on aarch64 in a container. The system compiler compiles the glue and links on both, and the C entry point takes `main`'s place by a linker entry symbol on macOS and by `--wrap=main` on Linux. Windows has not been attempted. No dynamically linked build: it saves disk and nothing else | 2026-11-12 |
| Window port | A crate of its own, `editor-platform`, whose one dependency is `editor-wait`, the typed time bounds: what a window reports as plain data, a scripted fake and a contract. `editor-platform-winit` is the adapter, and only it may name winit. The window is run by the main-thread service onto the editor queue, each event stamped when it was reported, and Lean closes it. A key carries its logical and physical identity and the modifiers, as W3C UI Events names, with the text it produced beside it; a pointer its action, position, button and modifiers; a resize the size and scale. The winit adapter produces all of it: the modifiers as winit last reported them, a key's text none for a release, for a control character and for a key pressed with Control or the system key held (that last awaits the owner), and the window's size reported as it opens. A window has a second listener, the drawer, for whatever draws in it: it is told that the window opened, with its native window as the port's own data, its size and its display's refresh rate, before anyone hears of the window; a new size, a new refresh rate, damage, hidden or shown; and that it is closing, last. Redraw is on demand: winit's loop waits, and the adapter never asks it for a redraw. The contract holds what is reported and what is told, and the real window is held to it under Xvfb; the drawer's shape awaits the owner | 2026-11-12, identity 2026-11-13, mapping and drawer 2026-11-14 |
| Clipboard port | `editor_platform::clipboard`: text read from the system clipboard and text written to it, with a fake that keeps text in memory and a contract of four properties. It is the Rust library's seam below the clipboard interface in Lean, which is the command loop's, and decides nothing of what the editor asks of a clipboard. `editor-platform-arboard` is the adapter, over arboard pinned exactly with its default features off; it needs no window, keeps one clipboard for its life, and reads an empty clipboard as no text. The gate touches no clipboard: the adapter is held to the contract under Xvfb, in one process and across two. Nothing binds it to Lean yet; a Wayland session is reached through XWayland or not at all. Where the port lives awaits the owner | 2026-11-14 |
| The editor's port | A composite: its requests are a sum of sub-ports (text, display, watch, clipboard, fuzzy, syntax tree, the editor state, the questions to the registry and config, and the loop's control of a running command), each reply its sub-port's. The watch port is the interrupt flag and the job clock, so the loop that asks them stays one pure program. A command is `EditorM`, a program over it; a sub-port's programs (`TextM`, `DisplayM`, `WatchM`) are lifted into it automatically, so config written at `EditorM` uses every text operation as it is. A refusal stays a `TextError`, the display's mapped to the text's of the same name; what the editor state refuses is a value in the request's reply. Each runner's state is the product of its sub-ports', but for the editor state: the command loop holds it and answers a command's state requests itself, with one pure handler, before the command's program reaches a runner, so the loop stays the one writer of editor state and rollback stays "keep the state from before". The editor API a command is written with is programs over this port; every operation that reaches the library has a case run on the models and on the real binding | 2026-11-13, state requests 2026-11-14 |
| Display contract | Lean publishes a scene of plain data after each command: views by handles (a snapshot, a scroll anchor and selections as markers), faces by name only. Layout answers two queries in the same call, the rows a view shows from its anchor and the position some visual lines away with the goal x passed back; Lean keeps no layout. A model lays text out in fixed-size cells, and one contract holds it and the real binding (over a fake shaper of that cell size) to the same properties. A key, a pointer and a resize cross the editor queue as words beside the event: the layouts are the table in `editor-ffi`'s `window.rs` | 2026-11-13 |
| Layout | `editor-layout`, ours, over a `Shaper` port whose fake gives fixed-size glyphs and whose real adapter is over Parley. Tabs are expanded before shaping; a row longer than 4096 bytes is laid out in segments. One immutable entry per segment, keyed by row and moved through the edit log's patches, rebuilt from the snapshot when a patch is refused; storage is sparse, with estimates and eviction, and no summarised tree yet. Decorations come from sources, asked for visible rows only; a face that sets no font attribute is paint only, and shapes nothing again. Positions, cursors and selections are found by a line's cells, a character's even share of its cluster's glyphs, so they are right whatever the order of a line's glyphs and however many characters a glyph draws. The frame is an immutable value with a content hash per row, and carries resolved paints, the id of the font each glyph is drawn in, the table of those fonts and the shaper's generation, never a face and never an atlas. A view's status fields are one row at its bottom, left fields from its start and right ones ending at its end, each padded in a box of its face's background, with no separator glyph; a face's vertical padding makes the row taller. A snapshot handle reaches its document's log and markers, so Lean's display binding needs only its table of snapshots. Layout lays out at a scale it is told, 1 until then: it multiplies a face's lengths by it in one place, as it asks the shaper for a font, so the `Shaper` port stays in physical pixels and the scale is in the cache key as the font; a change of scale alone shapes the rows a view shows again; frames and the queries' answers are physical pixels (the owner, 2026-11-14; where inside layout, and that nothing is rounded to whole pixels, await the owner). Who tells it a window's scale is so far one example; how a scene published from Lean is laid out at its window's scale is open. Who writes the cache while a render thread reads it awaits the owner ([concurrency.md](concurrency.md)) | 2026-11-13 |
| Shaping | `editor-shape-parley`, the `Shaper` port's real adapter, over Parley and fontique pinned at exactly 0.13.0; no type of either is public, and `deny.toml` lets no other crate depend on them. One Parley layout for each segment shaped, kept and broken again at another width; never `PlainEditor` or a layout of a document. Fonts come from a font set: given files as bytes with the system's fonts off, which every test uses over fixture fonts checked in under `tests/fonts`, or the system's, checked on demand. A glyph names the resolved font it is drawn in, fallbacks included, in a table that travels with the frame under a generation. Glyphs are in visual order with every line's base direction left to right; breaking is Parley's, at words; a line is as tall as the fonts on it; a carriage return and the Unicode separators break no line. It is built and held to the port's contract, and linked by nothing yet: the display handle stays on the fake until something needs real metrics through it | 2026-11-13 |
| Renderer port | `editor-render`, a crate of its own over `editor-layout` alone, owns the `Renderer` port: one method, a frame and a target in, what drawing it cost out. It publishes the port's fake and its contract, which both real adapters run, and holds what every back end shares: a mailbox where a newer frame replaces one not yet drawn; a scheduler that is a pure function of the demands and the time; the rule for which rows are built again, by their content hashes; the frame journal, with the times of each frame's input, draw and presentation; the counters; and the loop over them, which draws on demand, at most once a refresh, and waits with no deadline when idle. Time is a port with a fake. `editor-ffi` starts the render thread, one for the life of a window: a session makes the renderer when the window opens, on the window's thread, runs the loop on a thread of its own with the clock that stamps input, turns what the window tells into words left with the loop, and at closing joins the thread and drops the renderer on the window's thread. A hidden target is not drawn on, and what was asked meanwhile is served by one draw when it is shown. The render thread owns the renderer alone and never lays out ([concurrency.md](concurrency.md)). Nothing reaches the session from Lean yet. Where the port lives, and that the render thread and not the main thread draws, await the owner | 2026-11-14 |
| Rasteriser port | `editor-raster`, a crate of its own over `editor-layout` alone, owns the rasteriser port that makes a glyph's image: the trait, its key, request and image, the luminance bucket rule, `Fallback`, its published fake and its contract. Its adapters are swash's, in `editor-render-wgpu`, and Core Text's, in `editor-raster-coretext`, macOS's alone at run time. On macOS the renderer does what Core Text and native apps do: Core Text draws each glyph, in the grey of the run's luminance bucket (Core Text's own measured smoothing levels), as the user's `AppleFontSmoothing` says, and the painter places each glyph on Core Text's measured subpixel grid (thirds of a pixel at scale 1, halves at 2, whole pixels from 3) on every platform; swash draws what Core Text declines. Its masks are Core Text's own drawing to within the thresholds `mise run coretext-check` holds them to ([text-and-display.md](text-and-display.md), "The renderer, as built") | 2026-11-20 |
| Faces | A face is nine optional attributes: family, size, weight, slant, foreground, background, underline, strike-through, line height. Lean defines them, as a theme, an ordered list of definitions that config appends to in `setup`; Rust merges them, in layout, attribute by attribute: the selection over the view's decorations, a later one over an earlier one, over the face `default`, over base values, and a later definition of a name over an earlier one. Family, size, weight, slant and line height are a font, named to the `Shaper` port by a spec; the rest is paint. A length a face states (a size, a line height stated as a length) is in logical points, one physical pixel at scale 1, so `size := 14` is the same apparent size on every display; layout multiplies, and Lean states points and knows no scale for faces (the owner, 2026-11-14). The types keep the names they had when a theme stated physical pixels (`Pixels`, `Length::pixels`); renaming them awaits the owner. The theme crosses in the published scene's words, behind a presence, only when it changed; Lean's scene and the display interface are unchanged. Merging in Rust awaits the owner's confirmation (task `display-pipeline-text-core-pitfalls`) | 2026-11-13 |
| Rope | `ropey`, pinned at exactly 2.0.0-beta.1: indexed by byte, with rows split by line feed alone and UTF-16 counted in the tree, edits that return an error, and clones that share nodes. One private module of `editor-text` names it. `crop` is the fallback; a summarised tree of our own is left to the display layers | 2026-11-12 |
| Text model | UTF-8 only. A byte of a file that is not valid UTF-8 is kept as one reserved character, `U+10DC00` plus the byte, and saved as that byte, so an unedited save is byte-identical. Line endings are kept as they are. Positions are byte offsets on character boundaries; a row ends at a line feed alone; a point's column is in bytes, in UTF-16 code units or in cells, and no conversion clamps. A snapshot is the text at one revision, immutable and shared between threads, and is the only read view | 2026-11-12 |
| Edit model | Change sets on Helix's model: retain, delete and insert in bytes, in one normal form, for a text of one length. They apply, compose and invert, and map a position with a bias. A transaction is a change set plus optional selections, and applying one, all or nothing, is the one way a text changes and one revision. Ours: no published library counts in bytes over our rope or has the log | 2026-11-13 |
| Edit log | One entry for each applied transaction: its revision, an opaque 64-bit origin whose meaning is Lean's, and its changed ranges with four points each, from which the three tree-sitter takes are derived. Consumers pull one coalesced patch since a revision; a subscriber is a revision the consumer keeps. A range is traced to the entries that wrote it by walking the log. The log is dropped only when Lean forgets up to a revision | 2026-11-13 |
| Anchors and selections | An anchor is an offset and a bias, mapped at each transaction as Emacs moves its markers. A text holds markers, each an anchor or a selection under an id, and moves them all with every transaction it accepts. A selection is ranges of two offsets with one shape (exclusive, inclusive, line, block), kept sorted and merged, with a primary; its ends move as anchors, with biases that follow from the shape. What it covers is computed against a snapshot, in cells: a character, or a carriage return and line feed together. Evil's states map onto the shapes; its rules stay in Lean. Ours, with no library | 2026-11-13 |
| Motions | Motion primitives are questions of the text port, answered in Rust by walking the rope from a position, a cell at a time, so a motion moves over exactly what a selection covers: the next and the previous cell; the start and the end of the next and the previous word and WORD; the start of a line, its end and its first non-blank; the ends of the text; and rows up or down at a column counted in cells, which a point's column can be counted in too. A word character is an ASCII letter, digit or underscore or any character from U+0080 up, a rule the pure model can state: Vim's on ASCII, and not beyond it. One row and a range are read without the whole text. Which key runs which motion, counts, the wanted column and keeping a cursor on a line are evil's, in Lean. Ours, with no library | 2026-11-13 |
| Undo | In two halves. Rust keeps the inverse of every applied transaction and applies the inverse of a run of consecutive revisions as one transaction, where the text is in the state the run ended in; it hands back the selection in force before the run, and deleted text never leaves it. The revision only grows: an undo is a new revision that returns the text to an earlier state. The undo tree is Lean, over those two requests of the text port: groups whose boundaries the caller sets, undo, redo and branches, reverting the open group, and the state last saved. Every undo policy is Lean's, so other undo styles are written over the same primitives. Ours, with no library | 2026-11-13 |
| Excerpt buffers | The excerpt buffer is Rust; what goes in one is Lean. An excerpt buffer is a text the text port already speaks: motions, selections, transactions, layout's patches and the display's queries work on it unchanged. Its excerpts are anchors into source texts, its edits are transactions on those sources (so undo, the edit log and origin are the sources'), and its decorations are its sources' decorations, translated. Lean chooses the ranges, their context, order, grouping and headers. A Lean buffer kept in sync with its sources was considered and set aside: two copies, sync both ways, split undo, and edits attributed to the wrong text. Built so far (phase 1): an assembled text kept up to date from its sources' patches, joined by one line feed, motions crossing excerpt edges; (phase 2) edits through it as its sources' transactions, all or nothing, the dispatcher's guard of read-only and unheld sources, and undo through the excerpt buffer's steps; (phase 3) each excerpt's header drawn as a block above it, blocks counted by layout's rows and spot and by the follow, and the sources' highlights and buffer spans translated to every excerpt of them; (phase 4) the review buffer: a branch's change as hunks with context in Lean's order (tests first, then dependency), keep and revert per hunk, tracked excerpts whose time on screen the publish records, and a hunk never shown drawn in `review-unexamined` and counted in the status line | 2026-11-18 |
| Files | An `Fs` port that `editor-text` defines, with a published fake and a contract; `editor-fs-std` is its adapter over `std::fs`, a crate of its own, held to the contract by its own tests in a temporary directory. A load reads a file once up to the caller's limit, refuses a binary one, counts its line endings and changes none. A save is a temporary file beside the file and a rename, with the file's permissions, and is refused when the file on disk is not the one that was loaded, unless the caller overrides. One service thread in the library works loads, saves, stamps and directory listings in order, behind the completion queue; a listing answers a directory's entries with their kinds, links followed, sorted by name. The logic's tests make no real file, which the linter and `cargo-deny` hold. In Lean, load and save are requests of the job port, which a job awaits, and a refusal is a value. A job reads a snapshot a command took, by its id, from the table of snapshots the editor thread publishes and alone writes; what a job's load makes is the job's, named by a second kind of id, until the job's command takes it into the store, on the editor thread, and the runtime releases what the job held once that command has run. On the buffer's side: a buffer keeps its file's path, the stamp the last load or save answered and a line ending of its own, and its saved state stays in its undo tree. A path is matched to an open buffer by equality of the path string. Open and save are each a command, a job and the job's command: the buffer is made when a load's result is delivered, so the window does not change before the file is known to exist, and a save in flight is recorded in the editor state, so that its result is delivered by one request that cannot be interrupted and a second save is refused when it is asked. The line ending decides only the line break a command inserts; nothing is translated. The load limit is 1 GiB. Ours, over `std`, with `tempfile` for tests | 2026-11-13, buffers and commands 2026-11-14 |
| Processes | An `editor-process` crate holds the `Processes` port, its published fake, its contract and the service above it; `editor-process-std` is the adapter over `std::process`, with rustix for the two calls std lacks. Each child leads a process group of its own; a wait sees the exit without reaping (`waitid` with `WNOWAIT`), kills the group and only then reaps, so no signal reaches a reused group id and no straggler outlives its run. A run is a request of the job port, completed through the completion queue with the exit and both streams, or a refusal as a value; each stream has a limit, past which the group is killed and the run refused. Cancelling a job kills its child's group with `SIGKILL`; shutdown kills every group and blocks until every child is reaped, and the mains call it before they quit. The environment is the editor's, cleared, unset and set as asked. A streaming child is started, read, written and closed a request at a time: its output is framed in Rust by line or as bytes, a read is a pull completed once however fast the child writes, and each stream holds at most a bound of undelivered bytes, past which the child is held by not being read; a line longer than the bound ends it. A write waits until its bytes are in the pipe, and never raises `SIGPIPE`. A child does not outlive its job: the runner cancels it when the job ends. A descendant that leaves the group is not reached, and whether that is in scope awaits the owner | 2026-11-15 |
| File watching | An `editor-watch` crate holds the `Watch` port, its published fake, its contract, the coalescing rule and the service above it; `editor-watch-notify` is the adapter over `notify`, pinned at exactly 8.2.2, with no notify type public. The port watches directories only: a file is watched through the directory it is in, keeping the changes that name it, so an atomic save, a rename over the file and a remove followed by a new file are each seen, and a file not there yet can be watched. Coalescing is the core's, pure, with time passed in as milliseconds; no library debouncer is used. The window is fixed from a batch's first notice, not a trailing debounce, so a file written without pause is delivered once a window. Delivery is a pull, as a stream read is: one read pending a watch, completed once, its delivery drained when it is taken. A change is a path and a set of kinds, since FSEvents gives no order inside a record and can carry an earlier change's flag; real-file tests check that a kind is present. The bound, the caller's with no default, is how many distinct paths a batch may hold: past it, and on the platform's own overflow, the batch is one change, missed, on the watch's path. Each port registration is a notify watcher of its own, so registrations are independent, and the service shares one among the watches of one directory and depth. A watch is a request of the job port and does not outlive its job | 2026-11-15 |
| Vim scheme | Vim's grammar is one input scheme, pure Lean over a registry of Vim states: a key is bound to a part of speech named by its vocabulary name, a key sequence parses to an edit (a move, an operator over a target, a command), and the edit compiles to an invocation. Counts in any position multiply, and no count is not a count of 1. A register is named after a prefix bound in a keymap. The visual selection is not in the scheme's state: an operator in a visual state is an edit over the selection. Which Vim state a view is in is in the scheme's state, by view, so the next key is looked up in the new state's keymaps with no editor API. A key is walked through the active keymaps and then the state's, as one walk. | The session index and the version rule | One index file a run, `session-<run>.json`, written only by that run; a restore takes the highest run's whatever its format, reads a newer format leniently naming its unknown keys, and removes only earlier indexes of a format it understands, once its own is written; a newer or unreadable one is left as it is and said once | 2026-11-19 (session-restore phase 1) |
| The state directory's amendments | Session restore reads it at start-up, by a job, in place of lazily; and the headless host may be given one, `--state`, none by default | 2026-11-19 (session-restore phase 1) |
| Undo trees across a restart | Dropped: a tree never removes a node, and saving one means saving the kept inverse of every edge for the buffer's life (a whole-buffer change adds up to twice the buffer, about 20 MiB at 10 MiB each), with no bound and a read before `setup`, and rebuilding one needs an import of kept inverses down the text port, none of which exists. Each buffer a restore makes or reopens is marked (`Buffer.historyRestored`), and `u` at its root says `nothing to undo: no history before the restore`. If overturned, a per-buffer undo file written at a save, as Vim's `undofile` (task `persistent-undo-history`) | 2026-11-20 (session-restore phase 2) |
| Which stores are kept across a restart | An opt-in codec, not `ToJson`/`FromJson`: a store is kept only when its owner's `setup` registers `store.keptAcrossRestart (keep := …)`, `keep` being what of a value outlives the process; the same codec covers declared cells and workspace-table cells; the latest owner's wins, and twice in one `setup` is refused; a store with none is never written and starts empty | 2026-11-20 (session-restore phase 2) |
| Config's stores at a restore | Met by config's first install: the restore runs before config's `setup`, so config's declared cells are parked by the host (`Config.State.parked`) and its table cells by the reconciler (`Kept.parked`); the first install that declares one with a codec meets it as a reload meets a cell, and drops the rest, said. Parked values are written into every index until claimed, so a `setup` that throws loses nothing. A package's are met in the restore itself | 2026-11-20 (session-restore phase 2) |
| Shipped stores kept across a restart | `shell-history` whole, and `vc-review` with its review buffer's number dropped. Not the shell's output and run in flight, version control's status, commit and worktree records (buffer numbers), the project mode's listings (per run) or `working-sets` (its own file) | 2026-11-20 (session-restore phase 2) |
| Jobs running at a restart | Not restarted, and said stopped unless their owner starts them again. A job a person waits on registers itself reported (`workJob … (reported := true)`: the shell's run, the compile run, project search, version control's apply, hunk apply and commit), and the restore names each in `*restore*`. A job its owner starts again after the restart registers itself restarted (`workJob … (restarted := true)`: `check-files`, `follow-file`, the workspace's find, marker search and listing, the gutter's three and the restore's four) and is never said, since a watcher open as long as a buffer is would be said at every restart. Every other job running, a package's or config's (a save, a write, a read), is counted in the index, in `*restore*` and in the summary, since nothing starts it again. A change of the count alone starts no index write; the next write records it | 2026-11-20 (session-restore phase 2) |
| The session index, format 2 | New keys `frame`, `workspaces`, `stores` and `jobs`, and each view's `jumps`; nothing of format 1 changes. The number moved so that a phase-1 editor reads it leniently and leaves it, rather than remove it as understood; a format-1 index is read fully, with no frame | 2026-11-20 (session-restore phase 2) |
| A restored layout and config's | The index records the layout config had chosen (`Frame.chosen`) and the restore puts it back; until config installs, the publish passes over the default the host hands (`Kept.heldLayout`). A config that chooses the recorded layout keeps every restored tree, share and zoom; one that chooses another rearranges the same windows, as a reload does | 2026-11-20 (session-restore phase 2) |
| Which windows come back | Every window of every tab, tiled, docked and floating, with layouts, zooms, names, focus, the tab in view, selection and scroll. The start window keeps its id and becomes the focused window of the tab in view; every other view gets a new id. A window whose buffer is not kept shows `scratch`, said; a record the state refuses falls back to phase 1's placement, said. Not the wanted column, secondary cursors, marks, registers or buffer-local values (task `session-restore-marks-and-registers`) | 2026-11-20 (session-restore phase 2) |
| Jump lists across a restart | Kept as places in characters: a kept buffer's key or a file's path, with a row and a column, as `Jumps.detach` writes one; on restore a kept buffer's entry is held by a new marker, a path's attached once its buffer is restored, and an entry of an unkept buffer with no file dropped | 2026-11-20 (session-restore phase 2) |
| What the index costs per key | Nothing for stores on a key that moves none: the reconciler compares three revisions (the host's cells', the table's, the config generation) with those last mirrored and runs codecs only when one moved; a value is rendered only by the debounced write. Measured at 3.2 to 3.6 µs a key with two tabs, five windows, 100 jumps and a 10,000-line history | 2026-11-20 (session-restore phase 2) |
| Re-exec on macOS | Through a launcher inside the bundle: `Contents/MacOS/leanmacs` (`crates/editor-launch-std`) is the `CFBundleExecutable` and starts an editor by `exec`, in the same process, with `CFProcessPath` set to itself, so CoreFoundation's main bundle (and with it `NSBundle.mainBundle`, AppKit's app name and LaunchServices' check-in) is the app wherever the executable lives; `IO.appPath` is unaffected. A restart execs the launcher again (`--handover <record>`). Not a direct exec of a per-user executable: a cold start from Finder must reach one outside the signed bundle, and the fallback needs a process that outlives a failing one. Not a child process: LaunchServices registered the launched pid, and a child would be a second instance and miss the cold start's open-documents event. Held in the gate by the launcher's tests (`crates/editor-launch-std`, `identity.rs`), and seen once on a desktop ([lean-runtime.md](lean-runtime.md), "The app's identity across an exec"); the Dock icon's pixels are argued, not observed. Were an exec after AppKit's check-in seen to lose the identity, the editor's hand-over would become `open -n -a <bundle> --args --handover <record>`; the hardened runtime may make `CFProcessPath` ignored (task `recheck-cfprocesspath-under-hardened-runtime`) | 2026-11-20 (session-restore phase 3) |
| The restart's fallback | A probe before anything is handed over (`<target> --probe`, 10 s, `probe: ok` on its first line: what fails before `main` is refused and the editor keeps running); a hand-shake (the new run has restored the handed index and written its own, and removes the record); and a watcher the launcher spawns detached before each hand-over's exec, which on the process's end with the record still there marks the candidate failed and execs the launcher again, after 60 s killing it first. Candidates: the new executable, the previous, the shipped default, each once; with none left the record is renamed `handover.failed` and the next start restores the session and says so | 2026-11-20 (session-restore phase 3) |
| Editor updates and `:restart` | The same path: an update replaces `Leanmacs.app` in place, so `:restart` execs the launcher at the same path, which now holds the new build, with the session handed over. The probe refuses a new build that does not start; after the exec there is no previous build to fall back to, so a new build that fails before restoring leaves the session for the next start. Telling the user an update is waiting is task `restart-after-update-notice` | 2026-11-20 (session-restore phase 3) |
| The window across a restart | Closed and reopened, said: the echo area says the hand-over in the last frame drawn, and the new run's summary starts `restore: restarted, so the window was closed and reopened;` | 2026-11-20 (session-restore phase 3) |
| Input while a hand-over is in flight | Dropped, from the probe's success to the exec or until the hand-over is given up, with the hand-over said again; the editor does not leave meanwhile, and the restart waits for a save in flight before it writes the session, as a quit does | 2026-11-20 (session-restore phase 3) |
| The hand-over record | `<state>/session/handover`, text, one field per line, versioned (`leanmacs-handover 1`; `session`, `shipped`, `candidate`, `argument`, the launcher's `failed`), a value escaped `\\` and `\n`. Lean writes it once by a snapshot save; only the launcher and its watcher rewrite it; a launcher refuses a later format and starts the default with no hand-over. Not JSON: the launcher needs no JSON reader. One fixture, `tests/launch/handover-v1`, both sides read | 2026-11-20 (session-restore phase 3) |

| The launch flags and `--probe` | The executable's: `--launched-by`, `--shipped`, `--restore`, `--handed-over` and `--failed` (repeated) first on the command line, stripped before the mode is chosen (`Restart.Launch.strip`); the launcher's own options share no name with them.
